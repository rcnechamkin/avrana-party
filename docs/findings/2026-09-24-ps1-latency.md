# PS1 latency: what the first real-phone playtest shows, and a measurement system for the next one

Date: 2026-09-24 (night). Code: branch `experiment/ps1-title-profiles` (`ps1/stream_ps1.py`,
`ps1/index.html`, `ps1/tools/latency-report.py`). Labels: **REAL PHONE** = the owner's iPhone on the
party Wi-Fi; **WIRED SIM** = Playwright Chromium on the laptop over eth0 (not a phone, not Wi-Fi).

## Verdict

- The typical path is fast; **stalls are the problem.** REAL PHONE (playtest 20:28–20:38, 278
  visible seconds): input round trip **6 ms median** but **p99 1.4 s, max 2.2 s**; frame-presentation
  gaps **p95 0.6 s, max 1.6 s**; stalls in **~16% of seconds**.
- **The stalls hit TCP and UDP together** (WebSocket ping p99 1.5 s *and* the ICE/UDP pair round trip
  p99 0.74 s in the same seconds) while the server's send queue stayed empty → the **Wi-Fi link or the
  phone**, not Python, the encoder or the browser's JavaScript. *Inferred from correlation; the
  playtest had no kernel-ping or event-loop data, so it cannot be classified per spike.*
- **The Pi side is clean.** WIRED SIM steady state: capture→shown **p99 32.5 ms**, key injection
  **< 1 ms**, event loop never more than **10 ms** late, power `0x0`.
- **Prime suspect: the AP radio's power save is ON** (`iw dev wlan0 get power_save` → `on`), a known
  cause of 100 ms–2 s spikes on the Pi's Broadcom radio. Not changed (needs sudo; it is a network
  setting). The A/B test below proves or clears it.
- **Audio lags after stalls:** the phone's audio jitter buffer grew to **p50 276 ms, p95 1.27 s** — so
  sound can trail the picture by a second after a Wi-Fi stall. Expected to shrink with the stalls.

## Stages and how each is measured

| Stage | Where | Accuracy | How |
|---|---|---|---|
| A touch → input sent | phone | EXACT (one clock) | `pointerdown.timeStamp` → `performance.now()` at send |
| B input sent → Pi receives | phone→Pi | ESTIMATE (±½ best ping RTT, typically ±1–3 ms) | ack carries server receive time; clock offset from the lowest-RTT ping (4 Hz) |
| C Pi receives → key injected | Pi | EXACT | ack carries inject time |
| (emulator reacts, game logic) | Pi | **NOT MEASURED** | game-dependent, 1–3 frames; only a camera can measure touch-to-photon |
| E frame captured → shown | Pi→phone | ESTIMATE (clock offset) | **measure mode:** a 32-bit barcode in each frame (capture ms + injection counter); the phone decodes it at `requestVideoFrameCallback.expectedDisplayTime` |
| D touch → first frame captured *after* the injection is shown | phone | phone clock only | the barcode's injection counter; excludes the game's reaction and panel scan-out |
| WebSocket RTT | both | exact per round trip | 4 Hz ping |
| kernel ping Pi→phone | Pi | exact | **measure mode:** 5 Hz `ping`; the phone's OS answers even when its browser stalls |
| server event-loop lag | Pi | exact | how late a 20 ms sleep wakes |
| frame gaps, loss, jitter buffer, fps | phone | exact (WebRTC stats) | per second |

Spike seconds (WebSocket RTT or frame gap > 100 ms) are classified: **server** (event loop > 50 ms
late), **network** (kernel ping > 100 ms or unanswered, same or adjacent second), **browser/phone**
(kernel ping fine, WebSocket stalled), **unknown** (no kernel ping — e.g. a Windows laptop, whose
firewall drops pings).

## Changes made (and what they fix)

- **Log writes moved off the event loop** (the per-viewer log was written synchronously on the loop;
  an SD-card stall could delay input). Verified: loop lag max 10 ms with logging on.
- **Acks and pongs are handled immediately on the phone**, no longer queued behind WebRTC signalling.
- **Audio 20 ms frames** (earlier the same night): half the audio packets per viewer.
- **Auto-reconnect** on the phone page, so a stall that drops the connection recovers without a tap.
- No "optimization" was claimed faster without a before/after: the only proven wins are server-side
  (loop lag, CPU per viewer, earlier findings); the Wi-Fi fix needs the phone A/B below.

## Remaining suspects if power save is not it (ranked)

Phone-side Wi-Fi power management (iOS) · airtime contention from keyframe bursts every second
(`h264_i_frame_period=60`; try 180 with PLI recovery) · 2.5 Mbps target at 320×240 (1 Mbps would do)
· the channel (149, 20 MHz; neighbours) · WebRTC receive-side jitter buffer tuning (browser-owned).
